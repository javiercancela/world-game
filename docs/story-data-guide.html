01 / The package

One directory, one starting world.

A story is an authored package of JSON resources. It provides an initial world snapshot, character profiles, Fate action definitions, aspects, quest definitions, scene definitions, and a dialogue catalog. A campaign starts with a deep copy of that snapshot; play changes the campaign through typed events. It does not rewrite the story files.

The current repository contains one package:

02 / Assembly

How the loader combines the files.

load_story(directory=None, resources=None) in story/loader.py is the entry point. It returns a StoryPackage, which is the in-memory bundle consumed by the coordinator and persistence layer.

  1. Choose a source. Without a directory, use the installed package resource world_game/data/stories/gate_at_dusk. With a directory, read from that path. With a nonempty resources dictionary, parse its stored filename-to-text entries instead of reading the filesystem.
  2. Read eight fixed filenames. The loader has an explicit filename list. It does not scan the directory or discover additional resources through the manifest. Fixture files are not read here.
  3. Parse the manifest. Its resources set must equal the loaded filenames excluding manifest.json. A mismatch raises GameError.
  4. Parse the initial state. The whole entities.json object is validated as WorldState.
  5. Replace the aspect map. Parse aspects.json as a dictionary of Aspect, then assign it to state.aspects. This replaces rather than merges any aspects supplied in entities.json; the bundled world has an empty map there.
  6. Parse the remaining resources. Profiles, quests, and scenes are typed lists; rules and dialogue are typed objects. Preserve the original resource text in package.resources.
  7. Validate relationships and policy. validate_story() starts with validate_state(), then checks rules, definition references, compatibility constraints, and the authored player setup.
StoryPackage
├── manifest       ← manifest.json
├── initial_state  ← entities.json, with aspects replaced from aspects.json
├── profiles       ← profiles.json
├── rules          ← rules.json
├── quests         ← quests.json
├── scenes         ← scenes.json
├── dialogue       ← dialogue.json
└── resources      ← exact text of all eight runtime files

new_state(package, campaign_id, seed=None) deep-copies initial_state, assigns the campaign ID, sets content-hashed story and rules references, and replaces the placeholder random seed with the supplied seed or a fresh random 64-character hexadecimal seed. The authored snapshot remains reusable for another campaign.

Source: load_story(), new_state().

IDs are references; names and aliases are presentation.

The shared ID type is a string of 1–160 characters. Prefixes such as actor:, item:, portal:, and scene: are naming conventions; the basic ID type does not enforce a prefix grammar. Several particular IDs are nevertheless mandatory because the engine references them directly.

When a record says profile_ref: "profile:oren", the reference must resolve to the matching profile definition. For entities, the dictionary key must equal the record’s inner id. Preserve that same-key/same-ID convention for all keyed record maps, even where validation is less exhaustive.

actor:oren
  ├── actor.profile_ref → profile:oren          (profiles.json)
  ├── placement.container_id → location:gatehouse
  └── aspect:oren:blame
        └── grounding.id → proposition:oren_fears_blame

recover_ledger                                 (runtime quest ID)
  └── definition_ref → quest:recover_ledger     (quest definition ID)

identity.name is the display label; identity.aliases supplies reference vocabulary. Renaming Oren’s displayed name while preserving actor:oren is structurally different from renaming the ID. The offline interpreter and model prompts also contain authored vocabulary, so display-name changes may need corresponding parser and prompt updates.

Actors carry profiles, goals, and Fate sheets.

05 / Information boundaries

A fact can be true, hidden, or disbelieved.

The game separates canonical truth from what an actor knows and what an actor believes. This lets a convincing lie affect Oren without changing the underlying truth of Lea’s invitation.

RecordWhat it representsRelevant fields
PropositionA canonical statement. Truth is true, false, or unknown, stored as strings.id, predicate, arguments, truth, source, discovery_policy_id.
BeliefAn actor’s stance toward a proposition: believes, disbelieves, or uncertain.holder_id, proposition_id, stance, source_event_ids, acquired_tick.
KnowledgeStateWhat an actor has encountered or learned, including observations with provenance.known_entity_ids, known_record_ids, observations.
RelationshipA directed trust record, separate from prose and beliefs.from_id, to_id, kind: "trust", value (−2 to +2), source.
 
{
  "id": "proposition:lea_expected",
  "predicate": "expected",
  "arguments": {
    "subject_id": "actor:lea",
    "object_id": null,
    "value": null
  },
  "truth": "false",
  "source": {
    "kind": "story",
    "id": "gate-at-dusk@1.0"
  },
  "discovery_policy_id": "discovery:lea_expected"
}

At startup, Lea knows proposition:lea_expected and its false truth. Oren does not. A successful bluff creates belief:oren:invitation with stance believes; the proposition stays false. An authored verification can later change Oren’s stance to disbelieves.

The current proposition predicates are expected, incriminates, fears, and claim. arguments contains a subject ID, optional object ID, and optional string, integer, or boolean value. discovery_policy_id names authored provenance/policy; there is no generic plugin resolver that executes an arbitrary new discovery policy from this string.

Initial information is deliberately asymmetric.

  • Lea knows her invitation is false. She knows Sen exists, although Sen starts in another location.
  • Oren knows his own fear of blame. Lea does not initially know the corresponding aspect.
  • Sen knows the ledger incriminates the deputy. Asking her about the ledger emits an approved disclosure that adds the proposition to Lea’s known records.

An observation records record_id, a field (presence, placement, portal, speech, or presentation), a string or boolean value, source_event_id, and acquired_tick. Historical observations can remain after a record moves; they describe what was observed, not an unrestricted view of the current world.

Knowing an entity does not make it visible or reachable.

project() produces a filtered context for the interpreter, NPC, narrator, or decision role. Nearby entities, directly held items, adjacent portals and their endpoints, and conflict participants follow visibility rules. Known records, personal beliefs, and known grounded aspects follow separate filters. Models receive these views rather than the full canonical state.

Source: information records, project(), observe(), change_belief() and authored disclosure.

06 / Character voice

Profiles supply context, not world mutations.

{
  "id": "profile:oren",
  "actor_id": "actor:oren",
  "public": "A guard watching the gate.",
  "private": "Admit authorized visitors and avoid blame. You do not know the invitation truth.",
  "private_known_by": [
    "actor:oren"
  ]
}

profiles.json contains one profile for each actor. public and private are text fields of at most 4,000 characters. The validator requires the actor to exist and private_known_by to equal exactly [actor_id]. Every actor’s profile_ref must resolve to a profile ID.

When the coordinator voices an authored NPC utterance, it selects the speaking actor’s profile and sends its public description, private description, and actor goal IDs with that actor’s filtered context. This guides motive and phrasing. The response is constrained to the permitted authored response and supplied disclosure references.

The profile is separate from entity.identity.description. They currently repeat some public information, but editing a profile does not automatically update the entity’s visible description. Keep the two consistent where they describe the same character.

Private prose does not implement secrets or abilities.

Write important facts as propositions, knowledge records, aspects, or handler logic as appropriate. A sentence such as “Sen can unlock every door” does not bypass key and portal checks. If you add a secret to private prose, also author the structured fact and its permitted disclosure path when that secret must affect gameplay.

Source: Profile, profile validation, voice_npcs().

Discovering Oren’s concern can add Lea to known_by and award free invokes according to the create-advantage outcome. It does not need to invent the aspect during play: the hidden record already exists.

Grounding is checked during loading and after actions. Unsupported aspects are removed by events. Scene closing removes boosts and scene-bound aspects. Consequence recovery also follows explicit engine boundaries; treatment alone does not immediately erase a consequence.

A legal invoke can grant +2 or a reroll using a controlled free invoke or a paid Fate point. Knowing an aspect, having a valid grounding, and establishing relevance still matter; merely adding a phrase to narration does not grant an invoke.

08 / The ruleset

Rules configure registered engine behavior.

Check kinds and arithmetic

  • none: no roll. Both action and skill_id must be null. The action still checks permissions and may have effects.
  • static: roll four Fate dice against a fixed difficulty. Authored rule difficulties must be 0, 2, 4, or 6.
  • active: both actor and defender roll; opposition uses the defender’s selected skill rather than the rule’s static difficulty.
effort = sum(four dice) + acting skill + eligible stunt bonus + invoke bonus
opposition = fixed difficulty
          OR sum(defender dice) + defense skill + defender invoke bonus
margin = effort - opposition

margin < 0    → failure
margin = 0    → tie
margin 1–2    → success
margin ≥ 3    → success with style

Each Fate die is −1, 0, or +1. The Fate actions are overcome, create_advantage, attack, and defend. Outcomes depend on the action: an overcome tie can succeed at a minor cost; create-advantage outcomes depend on whether an aspect is new, known, or undiscovered.

The resolved plan can specialize the JSON check.

Physical attacks choose Athletics when defending Lea and Fight when defending an NPC. Creating an advantage against an actor uses Fight versus Athletics. Treatment chooses Craft or Influence by harm track and derives difficulty from consequence severity, adding 2 for self-treatment. These adjustments are in plan_action(), so the literal rule row is not always the final roll configuration.

Stunts are fixed +2 bonuses with eligibility conditions.

StuntEligible useAdditional requirement

A stunt must be on the actor’s sheet and in the selected rule’s permitted list, and its action, skill, handler, and goal must match. The engine adds 2 × number of eligible stunts. All three authored stunt definitions are required by validation.

Templates are bounded names, not executable expressions.

The initial aspect template catalog contains momentary_opening, noisy_intrusion, jammed_portal, off_balance, focused, cover, and burning. Creation methods are also constrained by handler logic and the typed template enum; adding a string to this catalog does not extend them.

The consequence catalog has exactly physical and mental tracks with three descriptions each: bruised, sprained_wrist, deep_bruising; and shaken, rattled_confidence, deep_distress.

Outcome names are validated, but effects remain implemented in Python.

The plan carries failure, minor-cost, and optional major-cost templates into relevant choice handling. Successful social, movement, lock, disclosure, and advantage effects are largely implemented by handler branches. In particular, changing outcomes.success or outcomes.style to another registered name does not generically dispatch that effect. A no-roll rule with no_effect in its outcome fields can still move an actor, transfer an item, or create an offer through its handler.

Source: HANDLERS and Intent, select_rule(), plan_action(), action_effects(), Fate outcomes, effect allowlist.

09 / Declarative guards

Preconditions describe opportunities.

Every bundled rule currently has an empty preconditions list. The format supports adding declarative guards. The list itself is an implicit AND: every predicate must evaluate true before the handler continues.

KindSubject / object / valueRuntime test
co_locatedSubject and object entity IDs.Both resolve to the same non-null location.
possessesActor subject and item object.Item is directly contained by the actor.
portal_statePortal subject; boolean value; portal_field is open or locked.Portal field equals the value. The field defaults to open.
has_known_beliefActor subject, proposition object, stance value.A matching personal belief exists; it does not test canonical truth.
aspect_activeAspect subject ID.Aspect exists and its grounding holds; visibility is a separate requirement.
quest_stageRuntime quest subject ID and stage value.Quest’s stage equals the value.
conversation_participantConversation subject and actor object.The actor is in the conversation’s participant list.

For example, this guard could be placed in a rule’s preconditions array to require both possession of the seal and a closed gate. This is an illustrative extension, not a predicate currently present in the package:

{
  "kind": "all",
  "children": [
    {
      "kind": "possesses",
      "subject_id": "actor:lea",
      "object_id": "item:royal_seal"
    },
    {
      "kind": "portal_state",
      "subject_id": "portal:gate",
      "portal_field": "open",
      "value": false
    }
  ]
}

Boolean nodes have 1–8 children. The story validator bounds predicate traversal to four levels and rejects missing subject/object references; it counts from the rule’s top-level predicates at depth 1. Use the documented record types for each predicate: the general reference check does not fully enforce every predicate’s subject/object type pairing.

These predicates add requirements to existing behavior. They do not remove handler rules such as co-location, active target status, possession, known concern, the failed-bluff lockout, or accepted transfer destinations. There is no arbitrary Python, JSON path assignment, SQL, or expression evaluation in a predicate.

Source: AtomicPredicate and BooleanPredicate, predicate validation, evaluate_predicate().

10 / Progression

Definitions and live instances are separate.

Quest definitions enumerate stages.

{
  "id": "quest:recover_ledger",
  "stages": [
    "active",
    "acquired",
    "completed",
    "failed"
  ],
  "terminal_stages": [
    "completed",
    "failed"
  ]
}

The live instance sits in entities.json.quests under the shorter runtime ID:

{
  "id": "recover_ledger",
  "definition_ref": "quest:recover_ledger",
  "stage": "active",
  "completed_objective_ids": [],
  "terminal_result": null
}

definition_ref links the instance to the definition. The instance’s stage is itself a closed enum of active, acquired, completed, and failed. terminal_result is null, success, or failure.

evaluate_quests() implements the actual ledger transitions: direct possession of item:ledger changes active to acquired; possessing it at location:gatehouse completes the mission. Completed objective IDs become ledger_acquired and then ledger_returned. Failure logic is authored in the scheduler and conflict/capture paths. The definition’s stage list validates the vocabulary; it does not encode those transition conditions.

Scene definitions describe locations; scene state manages resources.

{
  "id": "scene:gate",
  "location_ids": [
    "location:gatehouse"
  ],
  "stakes": "Recover the ledger; defeat means capture."
}

The definition holds id, location_ids, and stakes. The live SceneState holds an instance ID, definition reference, sequence number, participant IDs, GM Fate pool, deferred awards, and start tick. Initially, the instance is scene:gate:1, with Lea and Oren and a GM pool of 1.

boundaries() uses a hard-coded location-to-definition mapping for the three current locations. Moving to another location closes the previous scene and starts the corresponding scene when no conflict is active. During conflict, movement preserves the conflict scene. The engine’s roll stakes and context stakes are also authored in Python; the definition’s stakes text is not currently a general runtime stakes lookup.

Scene closing expires boosts and scene-bound aspects, clears relevant stress, processes deferred hostile-invoke awards, and checks recovery boundaries. SessionState tracks completed scenes, applied boundary IDs, NPC carryover credits, sequence, and whether the adventure is finished. Starting the app or reloading a save does not itself heal the character or refresh Fate points.

Scheduled effects resolve after time advances.

{
  "id": "schedule:deadline",
  "due_tick": 20,
  "priority": 0,
  "handler_id": "ledger_deadline",
  "args": {
    "actor_id": null,
    "item_id": "item:ledger",
    "portal_id": null,
    "quest_id": "recover_ledger"
  },
  "status": "pending"
}

A scheduled effect has id, due_tick, priority, a closed handler_id, typed args, and status pending, applied, skipped, or canceled. The only handlers are ledger_deadline and verify_invitation. Arguments can reference an actor, item, portal, and runtime quest.

The scheduler processes due pending effects in order of (due_tick, priority, id), with a processing limit of 20 per call. For normal committed actions the coordinator applies action effects, advances time, resolves due schedules, evaluates quests, expires unsupported aspects, handles boundaries, and records observations before committing.

The exact tick-20 behavior matters.

At or after tick 20, the deadline handler fails the mission only if the ledger’s direct parent is still location:records. It transfers the ledger to container:archive and fails the quest. If the ledger has already been taken, the deadline is skipped; it does not independently require reaching the gatehouse before tick 20. Because action effects happen before schedules, taking the ledger on the action that advances to tick 20 also avoids this removal.

A gate-bluff tie creates a verification effect due at current_tick + action_time_cost + 2: two ticks after that action finishes. If verification proceeds, Oren disbelieves the invitation and closes the gate; he can move to the courtyard to confront Lea. A terminal quest or inactive Oren cancels the applicable verification effect.

Offers and commitments preserve promises.

The initial maps are empty, but authored conversations can create collateral and key_loan offers. An offer stores proposer, recipient, transfer terms, a commitment, optional portal ID, expiry tick, source event, and status. Accepting it performs the permitted transfers and creates a durable commitment; speech alone does not transfer inventory.

A commitment names debtor, creditor, an item/recipient fulfillment predicate, a breach trigger, status, and source event. Returning Sen’s key can fulfill the loan. Leaving with the ledger and her key can break it and reduce trust. These consequences are engine branches, not inferred from private character prose.

Source: evaluate_quests(), offer(), accept_offer(), boundaries(), run_due(), time and commit ordering.

11 / Text and support data

Dialogue is packaged; fixtures exercise behavior.

dialogue.json

The Dialogue model has version and lines, a map of string keys to text. The bundled catalog is:

{
  "version": "dialogue-v1",
  "lines": {
    "gate_success": "Oren: The seal looks proper. Go through.",
    "gate_failure": "Oren: I need new evidence before I can admit you.",
    "collateral": "Oren: Leave the seal with me as collateral, and I will admit you.",
    "sen_greeting": "Sen: Lea! I am glad you came.",
    "ledger_secret": "Sen: The ledger shows that the deputy redirected relief supplies. Please preserve it.",
    "key_offer": "Sen: Take my key, if you promise to return it.",
    "verification": "Oren: The invitation could not be verified. Explain yourself.",
    "compel": "Sen asks you to deliver an archive receipt to Oren before leaving.",
    "victory": "You carry the recovered ledger outside the gate. The mission is complete.",
    "failure": "The ledger mission has failed."
  }
}
Current wiring: catalog stored, lines duplicated in code.

The loader validates this file and includes it in package persistence and hashing. Gameplay does not currently read package.dialogue.lines; authored lines and fallback output are literals in engine/actions.py, engine/scheduler.py, and related engine code. Editing this file changes the package content and hash, but does not automatically change the spoken line. To make it authoritative, add catalog lookups at the corresponding emission sites.

fixtures/demo.json

This has two branches, success and failure. Each contains a dice array and an ordered inputs array. Each scripted roll is four integers from −1 to +1. The success branch uses [-1, -1, 0, 0] for its first roll, reloads a saved pending choice, invokes Lea’s concept aspect, and completes the mission. The failure branch waits 20 times to trigger the ledger removal.

@reload is a demo runner directive that closes and reopens the database at the post-roll choice. It is not a normal player action or a story resource directive. Inputs such as /pass, /invoke, and /choose are executed by the CLI command path.

fixtures/eval-cases.json

The 30 cases test live interpretation and disclosure boundaries. Required case fields are id, text, handlers, goals, scene, clarification_allowed, forbidden_disclosures, and category. Some cases add methods, expected_targets, or require_new_claim.

The runner checks a returned action against allowed handler IDs, optional allowed goals/methods, target expectations, visible references, and prohibited disclosure substrings. It then probes actual engine admission and journal replay using scripted reactions. These cases measure interpretation and admission; they do not evaluate live NPC or narration quality. Their scene labels are evaluation setup hints, not scene definition IDs.

Neither fixture file is listed in manifest.resources, validated by load_story(), stored in StoryPackage.resources, nor included in the story package hash. The CLI demo and evaluation runner read them separately from installed package resources.

Source: run_demo(), evaluate(), demo fixture, evaluation cases.

12 / Worked example

“I show Oren the seal and ask for entry.”

This example connects the files to an actual resolution. Assume the initial world, a claimed authorization, and the first scripted roll in the success demo.

  1. Interpret an action against a filtered view.

    The interpreter sees Lea’s current surroundings, carried seal, known records, and known aspects. It proposes social_overcome targeting actor:oren, with goal gain_entry, method claim_expected_courier, and the seal in presented_item_ids. It does not choose success or mutate a portal.

  2. Select and admit gate.bluff.

    select_rule() finds gate.bluff. plan_action() checks Oren is present and active, Lea possesses any presented item, the quest has not ended, the bluff is a supported method, and no failed-bluff trigger blocks repeating it. The JSON supplies Deceive, difficulty 4, and a one-tick cost.

  3. Resolve the stunt from world data.

    Lea owns official_bearing, the rule permits it, the action/skill/goal match, and the presented seal has credential. The engine locks a +2 stunt bonus into the plan.

  4. Roll and offer a durable invoke choice.

    The four dice [-1, -1, 0, 0] sum to −2. Lea’s Deceive is 4, so −2 + 4 + 2 = 4 against difficulty 4: a provisional tie. The player can pass or make a legal invoke; the pending resolution stores the dice, plan, choices, and provisional resource balances across reload.

  5. Apply the chosen Fate outcome.

    In the demo, a paid +2 invoke of aspect:lea:concept raises effort to 6 and margin to +2: success. Lea’s Fate points fall from 3 to 2. Passing on the original tie instead admits her at a minor cost and schedules verification two ticks after the action’s completion.

  6. Emit, reduce, validate, and commit.

    The handler opens portal:gate, records Oren’s belief that Lea is expected, and emits the permitted speech. It does not change the proposition’s false truth and does not move Lea through the gate. The coordinator advances time, checks due effects and quests, updates observation/boundary records, validates the batch, and atomically commits it to SQLite. Narration presents that committed result.

One player statement can mention several actions.

The interpreter resolves the next consequential action of a compound plan. Gaining permission and then moving through the gate are distinct operations. A story rule opening the gate does not by itself relocate the player.

Source: interpreter contract, planning and effects, Coordinator, success demo.

13 / Portability

A campaign pins the resources it started with.

StoryPackage.resources retains the original text of the eight runtime files. The SQLite repository stores the package alongside the campaign, event journal, snapshots, durable pending choices, and history. Portable exports include the package so importing does not silently substitute the files currently installed on another machine.

package_hash() parses all resource texts as JSON, builds a filename-to-value map, canonicalizes it, and computes a SHA-256 digest. Formatting whitespace and object key order do not change that digest. Array order is generally significant; selected lists identified as semantic sets, such as known_by, participant_ids, stunt_ids, and known_record_ids, are normalized by the shared canonicalization helpers.

state.story_ref   = "gate-at-dusk@" + package_hash(package)
state.ruleset_ref = "fate-condensed-cli-v1@" + digest(package.rules)

The authored story_ref in the initial JSON is gate-at-dusk@1.0; the new campaign reference uses the content hash. Editing runtime text, including a stored but currently unused dialogue line, changes the package hash. Editing only demo/evaluation fixtures does not.

On package load from a save or import, the repository reconstructs the typed package from its stored resources and compares digests and pinned hashes. Existing campaigns therefore keep their saved story resources. Editing the checkout affects newly created campaigns that load those edited resources; it is not a migration of old campaign state.

Source: package_hash() and new_state(), canonical() and digest(), saved package and import checks.

Example: add a passive prop.

This valid entity could be added under entities.json.entities["item:chalk"]. It introduces an item in an existing room without creating a new rule or quest. It does not grant a “draw magic circle” action.

{
  "id": "item:chalk",
  "kind": "item",
  "identity": {
    "name": "Chalk",
    "aliases": ["chalk"],
    "description": "A short stick of white chalk."
  },
  "placement": {"container_id": "location:courtyard"},
  "item": {"tags": [], "quantity": 1}
}

Omitted optional components default to null. An item in Lea’s current room becomes visible through existing queries; it does not need to be prelisted as known by every actor. If the prop is an already known personal possession instead, author both its placement and the appropriate initial knowledge records.

A reliable editing sequence

  1. Identify the authoritative record. Use entity placement for ownership, portal components for passage state, propositions for truth, knowledge/aspects for disclosure, and profiles for voice.
  2. Preserve IDs and compatibility values. Change labels independently from references. If you must rename an ID, update every reference and inspect engine constants and prompts that use it.
  3. Keep definitions and instances aligned. Quest and scene references must resolve; profile references must be valid; initial player placement and scene should agree. Initial aspects belong in aspects.json.
  4. Validate the package. Run the CLI validation command below. Inspect generated schemas when uncertain about a field, enum, or bound.
  5. Exercise the affected behavior. Use the offline demo for the existing adventure paths, and a fresh test campaign for changed interactions. For code changes, run the relevant existing tests and add coverage for newly implemented behavior.
  6. Start a fresh campaign to see new package data. Saved campaigns retain their embedded package and state.
Custom-directory validation does not select that directory for play.

validate-story <directory> accepts a path, but world-game new loads the bundled package and only accepts the story name gate-at-dusk. There is currently no CLI option to start from an arbitrary copied story directory. The Python loader accepts a directory, so a custom launcher can explicitly use that API while respecting the same engine constraints.

Source: new and validate-story commands, directory loading, supported action behavior.

15 / Verification

Schema checks and world checks work together.

All story models inherit the shared Value base, configured with extra="forbid", strict validation, and assignment validation. Use JSON booleans, numbers, arrays, and nulls with their actual types rather than string approximations. Text fields are limited to 4,000 characters; identity names to 1–120 characters, and aliases to at most 20 entries.

Model validation checks shapes and literal values. Semantic validation checks supported references and world consistency. It is substantial but not exhaustive: a schema-valid string does not automatically have an implemented runtime meaning, and validation success does not prove every possible play path works.

Validation areaRepresentative checks
Physical stateEntity key/ID agreement, required components, existing parents, no containment cycles or item-as-parent, valid portal endpoints/key items, no open-and-locked portal.
Information and aspectsKnowledge holders are actors; known records/entities exist; belief/proposition arguments resolve; aspect subjects, knowledge controllers, scopes, and groundings are valid.
Fate stateStress within capacity, NPC personal points zero, all nine PC skills, correct authored allocation and three stunts, five PC character aspects, valid consequence slots.
DefinitionsUnique profile/scene/quest/stunt definition IDs, existing entry scene and state scene, nonempty valid location lists, quest stage membership and terminal-stage subsets, valid actor profile references.
RulesUnique rule IDs, required authored rule IDs, registered handlers and effects, permitted stunt references, supported argument/policy IDs, check-kind consistency, bounded difficulties, predicate references/depth.
Runtime linksConversation participants, offer transfer references, commitment parties/items, scheduled references, deferred awards, NPC credits, and conflict participants.

Useful commands from the repository root

# Parse and semantically validate the current package.
uv run world-game validate-story src/world_game/data/stories/gate_at_dusk

# Export the implemented schemas for inspection or editor tooling.
uv run world-game schemas --output /tmp/world-game-schemas

# Exercise the existing success and failure paths offline, including replay.
uv run world-game demo --no-color

# Check the loader, world invariants, and adventure integration behavior.
uv run pytest tests/unit/test_world.py tests/integration/test_adventure.py

The schema command writes WorldState.schema.json, EventBatch.schema.json, IntentResult.schema.json, PendingResolution.schema.json, and StoryPackage.schema.json. The package schema contains the nested manifest, rule, profile, quest, scene, and dialogue definitions; the world schema describes entities.json and nested aspect/entity types.

For an explicitly requested live interpreter evaluation, uv run world-game eval-live --output /tmp/world-game-evaluation.json uses the configured model/server and the evaluation fixtures. It is separate from ordinary offline validation and tests.
